# ADR-002: Control flow is a deterministic state machine, not an LLM orchestrator

## Status
Accepted

## Context
The six stages must run in order, each only after its check passes, and work
can go back to an earlier stage: failing tests go back to implementation (or
design if they keep failing), and review findings go back to design or
implementation, at most twice (decision D2). We need to decide who controls
this flow. Options considered:

1. **LLM orchestrator.** A "manager" agent decides what to run next and when
   to go back. Flexible, but it adds an extra model call at every step, can
   loop forever or skip a check, and its decisions are hard to reproduce or
   explain. Free-tier models are unreliable at this kind of planning.
2. **Separate Actions jobs chained with `needs:`.** Easy to read in the Actions
   UI, but `needs:` cannot express a loop. Going back to an earlier stage
   would require duplicating jobs or re-dispatching the workflow.
3. **Deterministic state machine in code.** A small Python driver holds the
   current stage and a retry budget, runs the stage, runs its check, and
   moves forward or back according to fixed rules.

## Decision
Use a deterministic state machine (option 3) as the control layer.

- The driver is ordinary Python, not an agent. It never asks a model "what next".
- Transitions are decided from **machine-readable results**, never from
  free text:
  - Stage check passes: go to the next stage.
  - Tests fail: go back to Builder, within the build-retry budget; when the
    budget is used up, go back to the Planner once; if it fails again, stop
    the run and explain why in `test_report.md`.
  - Reviewer verdict is structured (`approve`, `code_issue`,
    `approach_issue`): `code_issue` goes to Builder, `approach_issue` goes to
    Planner. After two review rounds the run ends and a human decides.
- The Reviewer runs as its own Actions job (see ADR-008) so that it has
  different permissions. The driver reads its verdict from `review.md`
  (frontmatter) and continues the loop.
- Every transition is appended to a run log (`run_state.json`) so any run can
  be followed afterwards (see ADR-004).

## Consequences
- Flow is predictable, cheap and testable without calling a model: the
  state machine can be unit-tested with fake stage results.
- Who goes back where is decided by code and a structured verdict, so a weak
  model cannot skip a check or loop forever; budgets are enforced in code.
- We lose flexibility: unusual cases (for example splitting a task in two) are
  not handled. Accepted because the issues are small.
- The Reviewer's verdict format is a contract. If a model returns malformed
  output, the driver treats it as a stage failure rather than guessing.
- Mixing a Python driver with a separate reviewer job needs care in the
  workflow design (how the loop re-enters the reviewer). This is an open
  point to resolve while writing the workflow, and may produce a superseding
  ADR.
- Related: ADR-001 (agent split), ADR-004 (state), ADR-007 (checks),
  ADR-008 (reviewer independence), ADR-009 (budgets).
