# ADR-005: Each agent gets a minimal tool set from its own small loop; GitHub writes are plain code

## Status
Accepted

## Context
We must decide which tools each agent has, how they are provided (MCP server,
`gh` CLI, REST API, own tools), and how to make sure an agent can do only what
it needs (decision D5). Models are free-tier and from two providers (ADR-006),
so the tool layer must not depend on one vendor's SDK. The free tiers also
impose small token limits (for example 8K tokens per minute and 200K per day
per model on Groq), so one tool call must never return a whole large file:
`block_parser.py` alone is several thousand tokens. Options considered:

1. **GitHub MCP server for all agents.** Rich, but exposes many write tools,
   needs extra setup, and is a large attack surface for an agent reading
   untrusted issue text.
2. **Give agents the `gh` CLI and a token.** Flexible, but an agent could push,
   comment or edit anything the token allows.
3. **A small set of local tools implemented by us** (read file, list files,
   search, edit file, run command), with all GitHub write actions done by
   workflow code outside the agent.

## Decision
Use option 3. Tools are our own functions, exposed to the model through a
small agent loop (or a model-agnostic toolkit such as mini-swe-agent). Each
agent has an explicit allow-list:

| Agent | Tools | Cannot |
| --- | --- | --- |
| Planner | read file, list/search files, write `spec.md` and `design.md` | edit source, run commands, touch git |
| Builder | read/search, edit files under `src/` and `tests/`, run commands (pytest, build) in the checkout | push, call GitHub, edit workflow files, read secrets |
| Reviewer | read/search, run commands (pytest, python) | edit files, push, comment |

GitHub actions (create branch, push, open PR, post the review comment) are done
by the **Release** step and a posting step in workflow code using `gh`/the
REST API, with the narrowest `permissions:` block for that job. Agents never
hold a GitHub token.

Tools are designed for small contexts:
- `read_file(path, start_line, end_line)` returns at most about 120 lines; there
  is no "read whole file" call.
- `search(pattern)` returns at most 20 matching lines with file and line number.
- `run_command` output is truncated to the last few dozen lines (failing test
  output is summarised to the failing test names and assertion messages).
- The agent loop keeps only the system prompt, the task and the most recent
  steps; older tool results are dropped from the conversation.

Enforcement is by construction: a tool that is not in the allow-list does not
exist for that agent. File tools reject paths outside the workspace and
outside permitted directories; the command tool runs with a scrubbed
environment (no API keys, no GitHub token) and a time limit.

## Consequences
- An agent cannot do anything we did not explicitly build, which is easy to
  reason about and to audit.
- We write and maintain the tool code and the loop ourselves (or adapt a
  toolkit), which costs time.
- The command tool can still run arbitrary code inside the runner. Containment
  is limited to the throwaway runner, the scrubbed environment and timeouts
  (ADR-009). It is not a true sandbox.
- Range-limited reads mean an agent can miss context that lies outside the
  lines it asked for, so weak models may make edits that ignore nearby code.
  This is accepted as the price of fitting free-tier token limits and is
  reported as a limitation.
- MCP is not used; the report should say this is a deliberate simplicity
  choice, not a statement that MCP is worse.
- Related: ADR-001 (agent split), ADR-008 (reviewer independence),
  ADR-009 (safety).
