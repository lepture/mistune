# ADR-008: The reviewer is isolated by job, model, prompt, permissions and evidence rules

## Status
Accepted

## Context
The assignment requires a reviewer that is independent of the other agents,
and asks how we stop it from simply agreeing with the implementer (decision
D8). A reviewer fails to be independent in several ways: it shares the
author's context or reasoning, it uses the same model with the same blind
spots, it can change the code it is judging, or it is easily persuaded by a
confident PR description. Models also tend to approve what they are shown.
Options considered:

1. **Same agent reviews its own work in a second turn.** Cheapest, but shares
   all context and blind spots. Rejected.
2. **Same model, fresh prompt and context.** Removes shared reasoning, but
   not shared blind spots.
3. **Separate job, different model family, own prompt, read-only, with
   evidence requirements.** Costs one extra model and some workflow
   complexity.

## Decision
Use option 3. Independence is enforced in five ways:

1. **Separate job.** The reviewer runs in its own Actions job on a fresh
   runner. Nothing from the Builder's job is available except what is
   fetched from GitHub.
2. **Limited inputs.** It receives only the issue text, the diff, and the
   repository at the pull request's head commit (ADR-003). It does not
   receive the spec, the design, the test report, the Builder's reasoning, or
   the PR description.
3. **Different model family.** The reviewer uses a different provider from the
   Planner and Builder (see ADR-006), so the two do not share the same
   training blind spots.
4. **Read-only permissions.** The job has `contents: read` only. It may read
   files and run code and tests, but it has no token that can push. The
   review is posted by separate workflow code, not by the agent.
5. **Own prompt with anti-agreement rules:**
   - The default stance is skeptical: the task is to find the strongest
     reason the change is wrong, then decide whether it holds.
   - It must run the code or tests itself and quote the evidence (command
     output, file and line) for every finding.
   - Verdict is structured: `approve`, `code_issue` or `approach_issue`, plus
     a list of findings with evidence. An `approve` with no checks run is
     rejected by the driver.
   - The driver overrides the model where facts are available: an `approve`
     is downgraded if CI on the PR head is failing.
   - It is not told to find problems whatever happens. It must not invent
     findings, so false alarms are also measured.

We will measure the result, not assume it: five seeded pull requests with
known flaws (and some correct ones) are fed to the reviewer, and we record how
many flaws it catches and how often it approves wrongly
(`experiment/seeded_prs/`).

## Consequences
- The reviewer cannot be influenced by the Builder's explanations, and
  cannot quietly repair the code it is judging.
- A different model family adds a second provider and key to manage; free
  tier limits apply to both.
- Not seeing the spec means the reviewer may raise points the spec excluded
  on purpose. Accepted (see ADR-003).
- Skeptical prompting can cause false rejections that waste a review round.
  We expect to tune this and will report both missed flaws and false alarms.
- Even so, independence is partial: both models are language models that may
  share some biases. This is a limitation to report, not a solved problem.
- Related: ADR-003 (hand-offs), ADR-005 (tools), ADR-006 (models),
  ADR-007 (checks).
