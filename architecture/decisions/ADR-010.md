# ADR-010: Triggers are a label or a comment from a trusted user, one run per issue at a time

## Status
Accepted

## Context
We must decide which events start the workflow, who may start it, and what
happens when two runs start at once (decision D10). Anyone can open an issue or
comment on a public repository, so the trigger is also a security boundary.
A bot that comments or pushes can also trigger itself.

## Decision
**Events:**
- `issues: labeled` where the label is `autose`: starts a full run for that
  issue.
- `issue_comment: created` where the comment is exactly `/autose` on an issue:
  starts a full run (same as the label).
- `issue_comment: created` where the comment is `/autose` on an open pull
  request created by this workflow: re-runs only the review stage (ADR-002),
  using the PR's latest commit.

**Who may start it:**
- The label requires triage or write access on GitHub by design.
- For comments, the job checks `author_association` is `OWNER`, `MEMBER` or
  `COLLABORATOR`; otherwise it exits without doing anything.
- Comments from the `github-actions` bot are ignored, so the workflow cannot
  trigger itself.
- Fork pull requests do not trigger anything (ADR-009).

**Concurrency:**
- One run per issue: `concurrency: group: autose-issue-<number>`, with
  `cancel-in-progress: false`, so a second trigger waits instead of cancelling
  work in progress.
- Different issues may run at the same time, within the model provider's rate
  limits.
- A trigger on an issue that already has an open `autose` pull request is
  refused with a comment, rather than creating a second PR.

## Consequences
- Strangers cannot spend our free quota or make the bot act.
- Only the owner or collaborators can start runs, so experiments need to be
  started from the owner account.
- A queued second trigger can run long after it was requested; GitHub keeps
  at most one pending run per group, so extra triggers are dropped. The
  refusal comment makes this visible.
- Related: ADR-002, ADR-009.
